# ai-backend — pending-wiring ledger

The debt this repo had no name for. A module lands, its wiring does not, and
nothing records the gap — so ten modules sat invisible for up to 2.5 months, not
because anyone abandoned them but because "built, not yet wired" is a state the
tree could not represent ([HANDOFF.md](../../plan/ai-backend-consolidation/HANDOFF.md)
§4–5). This is that record.

It is the companion to the ratchet: [`orphan_ratchet_baseline.txt`](../../../services/ai-backend/tests/unit/orphan_ratchet_baseline.txt)
is the machine-checked set (grow it and CI fails); this file is the **why** for
each entry, and it is what turns a scanner hit into a decision.

**It supersedes [DELETE-REPLACE.md](DELETE-REPLACE.md) §B.** That section proposed
deleting ~8,600 LOC of "unreachable code" across 10 modules. Reading all 23 current
orphans against source says the genuinely-safe-to-delete-now set is **~45 LOC, and
possibly zero without an author's sign-off** — every other entry is blocked on named
work, ready to wire, or not actually an orphan.

Generated by reading each module's source + docstring + `git log` (5 parallel
readers, 2026-08-01). "Run it, don't read it": three claims in the audit and the
execution plan did not survive contact with the source — see §Corrections.

**Updated 2026-08-06.** The counts below are no longer the 23 that paragraph describes,
and the "~45 LOC, possibly zero" figure is now historical. Two things moved that day:
closing the scanner's facade blind spot lifted **15** already-unreachable modules into
view at once, and then **35 modules (12,340 LOC) were deleted after an audit** — see
§Retired for what the audit changed, including the 13 modules it held back and the two
it pulled out of the delete set. The disposition table is current; the prose above is
kept as written on 2026-08-01.

## Disposition — the four states an "orphan" can be in

| State             | Meaning                                                                                      | Count |
| ----------------- | -------------------------------------------------------------------------------------------- | ----: |
| **Blocked**       | Names a specific **unshipped** dependency (route, hook, consumer, column). Cannot wire yet.  |     7 |
| **Newly visible** | Already unreachable; the scanner could not say so until the facade blind spot was closed.    |     2 |
| **Wireable**      | No unshipped blocker — every dep is present; the decision is **wire-or-drop**, not a wait.   |     2 |
| **Delete**        | No blocker **and** superseded by a wired twin / stale shim / redundant scaffolding.          |     0 |
| **Not an orphan** | Live `python -m` entrypoint (`__main__` guard) the scanner mis-flags. Exclude from the scan. |     1 |
| **Retired**       | Module since deleted; row kept for provenance.                                               |    42 |

**The rule that governs deletion** (adopted in [TASKS.md](../../plan/ai-backend-consolidation/TASKS.md)):
nothing **younger than 30 days** is deleted without asking its author. As of
2026-08-01, **12 of the 23 are <30 days** (added after 2026-07-02) — so most of even
the Delete/Wireable set is "confirm first," not "remove now."

### The ratchet cannot see these two — a package `__init__` hides an orphan

**Half-resolved.** The scanner follow-up this section asked for shipped: `orphans.py`
no longer lets a package `__init__` vouch for its own submodules. It resolves the
re-export instead — `from pkg.mod import Thing` records that `pkg.Thing` MEANS
`pkg.mod`, and only an import from **outside** the package spends that credit. That
lifted 15 modules (4,825 LOC) into view at once, `coordination` among them; it is now
in [`orphan_ratchet_baseline.txt`](../../../services/ai-backend/tests/unit/orphan_ratchet_baseline.txt)
like any other entry, and the §"Newly visible" table below carries the rest.

**`handoff` still is not machine-visible, and for a different reason.** It is imported
by `coordination.py` — a real module, not a facade — so one-hop reachability scores it
used. But its only importer is _itself_ an orphan, which makes it a **transitive**
orphan: dead code reachable only from other dead code. Catching that needs true
reachability from entry points, not the one-hop "does anything name it" test this
scanner runs, and that is a materially bigger change with a much larger false-positive
surface. Until someone takes it on, `handoff` stays recorded here **by hand** — and the
general shape ("wired to an orphan" is not wired) is worth remembering, because deleting
`coordination` without it would strand 202 more lines.

Two clusters dominate: the **todos/memory extraction pipeline** (`proposal_extractor`,
`todo_extractor`, `postgres.todo_extraction_store`, and cross-service `routine_scheduler`)
all wait on the same missing **P3-A1 / P5-A1** orchestrator + backend endpoints; and a
**release/harness conformance** cluster (`operational_corpus`, `release.promotion`,
`context_origin_conformance`, and the Wireable `e2_final_conformance`) all wait on a
Step-15 / CI driver. `promotion_cohorts` was the fourth member until the F3
capability-discovery deletion removed it — it imported `CapabilityActivationMode`,
so it could not outlive the package — and `operational_corpus` was orphaned in the
same stroke, having had no other `src` importer.

## Retired — module since deleted (42)

Recorded rather than silently erased, for the same reason §"Wired up" is: a future
reader who finds a row here and no module needs to know that was deliberate.

**2026-08-06 — 35 modules, 12,340 LOC, deleted after audit.** The owner asked for
the orphan set to go and for an audit first. What the audit changed:

1. **Scope was 50, not 30.** Deleting the 30 flagged modules strands whatever only
   _they_ reached. Iterating the scanner to a fixpoint added 15 more (wave 2) and 5
   more (wave 3) — `subagents.handoff` is the shape: `coordination.py` imports it, so
   one-hop reachability scores it used.
2. **Unreachable did not mean unclaimed.** 33 of the 50 are named in planning docs.
   13 were held: `coordination`/`handoff` (open ARQ-006/ARQ-012), the F1 and
   Step-15 conformance clusters (open "Needs your decision"), `mcp.credentials.*`
   (waits only on the P2-8 flip; its backend endpoint shipped in `d472c80b`), and
   `workspace.patch_plan`.
3. **`effects.composition` and `effects.conformance` were pulled back out.** Both
   scanned as wave-2 orphans, but `release/e2_final_conformance.py` — a **held**
   module — imports them, so deleting them would have broken something kept.

Three checks were run first because deleting them would have removed a _control_
rather than dead weight, and all three came back clean: skill visibility is enforced
through the subagent authority path, not the deleted `skills.policy`; a live audit
chain exists in `file/_audit_manifest.py` and `runtime_api/http/audit_list_routes.py`,
separate from the deleted `records.audit` type; and `RUNTIME_FIELD_ENCRYPTION` had no
consumer and no settings knob left.

**One thing this deletion owes the compliance record.**
[data-persistence-retention.md](../flows/data-persistence-retention.md) cites C7
envelope encryption as an implemented control, pointing at
`agent_runtime/persistence/encryption.py`. That file is gone. It was never a _working_
control on the shipping product — cluster 03 F11 records that field encryption applied
only to the Postgres adapter and that the desktop is plaintext-at-rest by design with
`NullFieldEncryption` as the default — but the implementation those docs point at no
longer exists, and a compliance reviewer must be told that rather than left to find it.

## Not an orphan — live entrypoints the scanner mis-flags (1)

Has an `if __name__ == "__main__"` guard and is invoked via `python -m`. The
scanner ([`orphans.py`](../../../tools/ai-backend-smells/orphans.py)) excludes entry
points by **leaf name** (`__main__`, `app`, …) and does not look for a `__main__`
_guard inside the file_, so this read as unreachable when it is not.

- **`runtime_worker.local_release_control_cli`** (560, 07-27) — the dev/dogfood
  release-control CLI; its server router is mounted at `runtime_api/app.py:491`.
  [FINDINGS.md](FINDINGS.md) §L85 already flagged it as "a genuine CLI, correctly excluded."
  **Not deletable.**

**Scanner fix — done.** `orphans.py` skips any module with a top-level
`if __name__ == "__main__":` guard (AST-detected, so a docstring mention does not count),
and both entries were pruned from `orphan_ratchet_baseline.txt` at the time.

**Second scanner fix — done (2026-08-06).** Two more things stopped counting as evidence
of use: a package `__init__` re-exporting its own submodule (resolved through the facade
instead of trusted), and a dotted string literal that merely looks like a module (a logger
channel was clearing a genuinely unwired 907-line job — `routine_scheduler` — out of the
report). The scan now reports **30** orphans against a 30-line baseline, and
`test_baseline_has_no_entry_the_scanner_cannot_reproduce` fails on a line the scanner can
no longer justify, so the "catches debt appearing, not debt clearing" asymmetry noted in
§"Wired up" is closed.

## Wired up — blocker shipped, row retired (2)

The state this ledger exists to reach. Recorded rather than silently erased, because
"it was pending once" is the provenance a future reader needs when they find the
module already wired and wonder whether that was deliberate.

- **`agent_runtime.capabilities.mcp.connector_resolver`** (75, enrolled 08-02) — waited on
  **P2-6** and **P2-8**; both shipped. `runtime_worker/stream_tools.py` imports
  `ToolConnectorResolver` and publishes it per run (`publish_connector_resolver`, P2-6),
  and `per_tool_registration.py` resolves it off the catalog under the P2-8 registration
  flip (`833e7d25`).
- **`agent_runtime.capabilities.mcp.connection`** (117, enrolled 08-02) — its row's claim
  ("nothing in the running app imports this module yet") stopped being true at
  **P2 Wave 1** (`498ec9a5`): `tool_source.py`, `per_tool_registration.py` and
  `proxy_plane.py` all import it, and all three are reachable from `runtime_api.app`.

Both were pruned from [`orphan_ratchet_baseline.txt`](../../../services/ai-backend/tests/unit/orphan_ratchet_baseline.txt)
later than they should have been — the wiring commits did not prune in the same change,
and the ratchet only failed on **new** orphans, so two stale entries rode along silently.
That asymmetry was the ledger's one blind spot: it caught debt appearing, not debt clearing.

**Closed 2026-08-06.** `test_baseline_has_no_entry_the_scanner_cannot_reproduce` now fails
on a baseline line the scan cannot justify, so wiring a module up — or deleting it — forces
the prune in the same change. It found a third rider immediately:
`runtime_worker.jobs.encrypt_existing_columns`, whose module the Postgres removal deleted
while leaving the line.

## Ownership

Git first-commit author is the provenance signal, not the semantic owner: the
2026-05 modules are `parthpahwa1`'s; the 2026-07 modules were landed by the
automation account `0x-copilot-dev` on behalf of a program. The **actionable owner
is the PRD / step named in "waits on"** — P3-A1 and P5-A1 (todos/routines), C1
(workspace overlay), Step 15 (promotion/release), PRD-FS-04 (retention),
F6.1 (provider hints), team-memory-cmdk §9 (proposals). Ask there before deleting a
<30-day module, and wire there when the blocker ships.

## Method

`git -C <worktree> log --diff-filter=A` for provenance; the module docstring + a
`grep` of `services/ai-backend/src` for each named blocker to confirm it is truly
absent (and to catch same-name collisions — `promotion`, `retention`, and
`reconciliation` each have a wired same-named sibling that inflates the scanner's
mention count). Every "waits on" is quoted from source, not paraphrased.
