# Why does the desktop app need SQL? Postgres, or SQLite?

**Audit date:** 2026-08-03 · **Method:** source-level read of `services/backend`, `services/ai-backend`, `services/backend-facade`, `apps/desktop`, `tools/desktop-runtime`, plus forensics on the live install at `~/Library/Application Support/0xCopilot`. Every non-obvious claim carries `file:line`.

---

## 1. The one-paragraph answer

The desktop ships and boots PostgreSQL 17 for exactly one reason: **`services/backend` has no other storage backend, and it fails closed without one.** `DesktopComposer.REQUIRED_ENV` lists `DATABASE_URL` first and `validate_env` refuses to build the app without it (`services/backend/src/backend_app/desktop_app.py:97-123`), then `create_desktop_app` calls `PostgresConnectionPool.shared(...)` with no alternative branch (`desktop_app.py:278`). The supervisor's `postgres` phase is correspondingly unconditional — no env var, no flag, no `if` guards it (`apps/desktop/main/services/supervisor.ts:137-148`). It is **not** needed for the agent runtime: `ai-backend` defaults to the file-native store (`resolveAiStoreBackend` returns `"file"` for unset/empty/unrecognised flags, `apps/desktop/main/services/service-env.ts:566-576`), whose read path is _already SQLite with FTS5_ (`services/ai-backend/src/runtime_adapters/file/_catalog_index.py:46-119`) and whose LangGraph checkpointer is _already `AsyncSqliteSaver`_ (`services/ai-backend/src/agent_runtime/execution/deep_agent_builder.py:463-479`); the `atlas_ai` database is `CREATE DATABASE`'d on every boot (`supervisor.ts:144-147`) and then never migrated or connected to (`apps/desktop/main/services/desktop-supervisor.ts:294-298`). And it is **not** needed for the third service: `services/backend-facade` contains zero `psycopg`/`sqlalchemy`/`asyncpg`/`DATABASE_URL` references anywhere in `src` or `requirements.in` (verified by grep). So 66 MB of staged binaries and a six-process postmaster exist to serve one service whose actual SQL usage — measured across its 277 `.execute(` sites and 78 tables — is **2 JOINs, 0 CTEs, 0 window functions, 0 executed `SKIP LOCKED`, 0 executed `LISTEN/NOTIFY`**, against a schema where roughly half the tables are multi-tenant/SSO machinery a single-user install can never reach.

### 3b. `atlas_ai` — 69 tables, **0 of them created on a default desktop boot**

The database is `CREATE DATABASE`'d every boot (`supervisor.ts:144-147`) and the migration gate then returns early on the file backend (`desktop-supervisor.ts:294-298`). Live-install forensics confirm it: `base/16384` is 7.4 MB / 299 files — byte-for-byte the file count of `template1` and the stock `postgres` database — while `base/16385` (`atlas_backend`) is 13 MB / 775 files and contains all 79 backend table names plus `_yoyo_migration`.

All 69 are therefore **CLOUD** on desktop. Grouped:

- **Core chat (4):** `agent_conversations`, `agent_messages`, `agent_runs`, `agent_conversation_tool_ordinals` — conversations/threading/runs, and monotonic per-conversation tool ordinals.
- **Event ledger + queue (2):** `runtime_events` (per-run `sequence_no` ledger backing SSE resume), `runtime_outbox_events` (the worker command queue — the _only_ real `SKIP LOCKED` in the product, `runtime_api_store.py:7015`).
- **Approvals (3):** `runtime_approval_requests`, `runtime_approval_batches`, `runtime_approval_batch_items` — the human-in-the-loop gate. `runtime_approval_batch_items` has **no `org_id` column** (`0001_runtime_baseline.sql:163-171`), so its tenant scope is reachable only by joining `runtime_approval_batches`; this is the densest genuine JOIN cluster in the runtime (6 of the 16 JOINs in `runtime_api_store.py`).
- **Tool + audit (3):** `runtime_tool_invocations`, `runtime_audit_log` (hash chain + plpgsql immutability trigger + `audit_writer` role GRANT), `runtime_citations`.
- **Artifacts (11):** `runtime_artifacts`, `_revisions`, `_idempotency`, `_reference_edges`, `_gc_candidates`, `_gc_candidate_scopes`, `_gc_quarantine`, `runtime_artifact_cleanup_schedule_state`, `_deferred_tenants`, `_tenant_executions`, `runtime_stage_commit_ledger`. Note: artifact **bytes never enter Postgres** — even the Postgres bundle uses `FileArtifactBlobStore` on a filesystem root (`runtime_adapters/factory.py:660-671`).
- **Usage / billing (11):** `runtime_run_usage`, `runtime_model_call_usage`, `model_pricing`, `runtime_usage_daily_{org,user,connector,subagent,purpose}`, `runtime_usage_attribution_edges`, `runtime_context_occupancy`. The only place a query planner does real work (`GROUP BY`/`SUM` over 5 dimensions) — and CLAUDE.md already assigns billing/usage rollups to `backend`, not here.
- **Budgets (3):** `usage_budgets`, `usage_budget_state`, `usage_budget_reservations` — `row_version` CAS + per-run reservations, i.e. cross-process spend racing.
- **Retention / legal (4):** `retention_policies`, `runtime_legal_holds`, `runtime_deletion_evidence`, `runtime_consumer_cursors`.
- **Drafts / shares (4):** `runtime_drafts`, `runtime_draft_effect_supersessions`, `conversation_shares`, `conversation_share_recipients`.
- **Effects / overlays (2):** `runtime_effect_claims` (at-most-once external side effects), `runtime_workspace_overlay_manifests`.
- **Fleet scan state (6):** `runtime_audit_export_verification_{manifests,outcomes,scan_state}`, `runtime_repair_planning_{snapshots,outcomes,scan_state}` — `(source)`-keyed cursors with `FOR UPDATE` leases so only one of N sweepers advances.
- **E2 legacy-stage migration (5):** `runtime_e2_legacy_migrations`, `_stage_migrations`, `_stage_reservations`, `_stage_reconciliations`, `_stage_evidence` — one-shot data migration, which CLAUDE.md explicitly lists as _not_ belonging in ai-backend, and which taxes the hot path (`_requires_legacy_stage_run_fence` puts a `SELECT … FOR UPDATE` on `agent_runs` into `append_event`, `runtime_api_store.py:6423-6456`).
- **Misc (1):** `workspace_defaults` — org-level default model / connectors / behaviour.
- **Never written (11, verified `INSERT INTO` count = 0 across `src/`):** `runtime_async_tasks`, `runtime_subagent_results`, `runtime_capability_snapshots`, `runtime_consumer_cursors`, `runtime_memory_scopes`, `runtime_memory_items`, `runtime_checkpoints`, `runtime_compression_events`, `runtime_context_payload_blobs`, `runtime_tool_budgets`, `runtime_context_payloads`. Plus `todo_extractions`, which has an `INSERT` (`postgres/todo_extraction_store.py:75`) inside a module with zero non-test references. `runtime_checkpoints` is the sharpest case: it is the _only_ table in the service any window function touches (two `ROW_NUMBER() OVER (PARTITION BY …)` retention sweeps at `runtime_api_store.py:5101,5335`) — the most planner-dependent SQL in ai-backend runs against a write-never table, while the real LangGraph checkpoint tables are created at runtime by `AsyncPostgresSaver.setup()` and appear in no migration file.

| `pg_advisory_xact_lock`    | 5                                                                                         | 15                    | 5                                        |
| `FOR UPDATE`               | 15                                                                                        | 49                    | 15                                       |
| `FORCE ROW LEVEL SECURITY` | **0** in applied migrations (22 in `migrations/staged/do_rls.sql`, which nothing applies) | —                     | **0**                                    |

**Honest verdict: on desktop, almost nothing.** Item by item:

1. **`FOR UPDATE SKIP LOCKED` — not used at all in `backend`.** All 8 occurrences are docstrings describing a Postgres adapter that was never written: `library/index_jobs.py:7`, `todos/store.py:453`, `todos/service.py:684`, `webhooks/store.py:145,194`, `webhooks/rotation_worker.py:7,22`, `webhooks/service.py:403`. There is no `PostgresTodosStore`, no `PostgresWebhooksStore`, no `PostgresLibraryIndexJobsStore`. `LibraryIndexerLoop` (`jobs/library_indexer.py:262`) is instantiated nowhere outside its test. The one real queue in the product is `runtime_outbox_events` in ai-backend (`runtime_api_store.py:6993-7047`) — which the desktop does not run, because it uses the file store's queue: a linear scan of `self._queue_order` under one `asyncio.Lock` with a JSONL ledger for durability (`file/runtime_api_store.py:4149-4204`), backed by `RUNTIME_START_IN_PROCESS_WORKER=true` (`service-env.ts:600`), i.e. exactly one claimer. **Breaks without it: nothing.**

2. **`LISTEN/NOTIFY` — zero executed statements in `backend`.** Every SSE fan-out is an in-process condition variable (`InMemoryHomeActivityBus`, `InMemoryInboxActivityBus`, …); `LISTEN/NOTIFY` appears only in aspirational comments (`projects/sse.py:162`, `inbox/sse.py:189`, `home/sse.py:184`, `memory/sse.py:105`, `palette/refresh.py:1`). In ai-backend it is real and load-bearing _in production_ — `settings.py:574-581` states its purpose plainly: API and worker are separate processes, so `InMemoryEventBus` cannot wake the SSE handler. The desktop pins `RUNTIME_EVENT_BUS_BACKEND=in_memory` (`service-env.ts:622`) precisely because API and worker share one process. **This is the one primitive with no SQLite analogue — and it is switched off on desktop by two independent guards.**

3. **`pg_advisory_xact_lock` — 5 real call sites in `backend`,** all guarding an audit hash chain from forking (`store.py:339-354`, `store.py:671`, `store.py:1192`, `connectors/store.py:837`, `projects/store.py:1156`) plus one per-scope MCP descriptor lock (`mcp_revision_store.py:332-341`). The invariant is real; the mechanism is not portable. **Breaks without it:** two concurrent appenders read the same `prev_hash` and fork the chain. The SQLite replacement is `BEGIN IMMEDIATE` at the top of every affected transaction — cheaper in mechanism, _more_ expensive in scope: the advisory lock is keyed per `(table, org)` and collisions merely "cause extra serialization of unrelated chains", whereas `BEGIN IMMEDIATE` takes a database-global write lock.

4. **Row-Level Security — 26 `ENABLE ROW LEVEL SECURITY` in the applied backend migrations, ~45 policies, and it enforces nothing on desktop.** Three independent reasons, each verified: (a) **zero** `FORCE ROW LEVEL SECURITY` statements exist in any applied migration (all 22 live in `migrations/staged/do_rls.sql`, which is referenced nowhere outside docs), and Postgres exempts the table owner from non-FORCEd RLS; (b) the desktop connects as `atlas`, the **initdb bootstrap superuser** (`postgres.ts:209-216` runs `initdb --locale=C -U atlas --auth=scram-sha-256`; `service-env.ts:71,85` builds every DSN from `PG_SUPERUSER`), and superusers bypass RLS unconditionally; (c) the `single_user_desktop` profile sets `enforce_rls=False` (`deployment_profile.py:102-112`), and there is exactly one tenant. Additionally, five policies (`api_keys`, `auth_provider_domains`, `privacy_settings`, `tool_use_policies`, `wallet_identities`, `0001:1617-1673`) read `app.current_org` while `_apply_rls_session_vars` stamps `app.current_org_id` (`store.py:357-380`) — they could not match even if enabled. **What RLS costs today: one `set_config` round-trip per transaction, enforcing nothing.** It remains genuinely load-bearing for the cloud deployment.

5. **`plpgsql` immutability triggers + role GRANTs** on `identity_audit_events` / `mcp_audit_events` / `skill_audit_events` (`0001:1322-1326`). The trigger half ports directly (SQLite `CREATE TRIGGER … BEGIN SELECT RAISE(ABORT,'…'); END`). The GRANT half — "only the `audit_writer` role may write" — is already void on desktop for the same reason as RLS: the connecting role is the superuser that owns the objects, and the `enterprise_app`/`audit_writer` roles the `DO $$` blocks target do not exist there (they no-op on the `pg_roles` check). **Real delta on desktop: the trigger, which ports.**

6. **JSONB is a blob, not a query surface.** Across the entire MCP, connectors, adapter-registry, projects, settings and revision surfaces there is not one `->>`, `@>`, `jsonb_*` operator or JSON index — only write-side `%s::jsonb` casts (`connectors/store.py:693,725,861`; `adapter_registry/store.py:322,574`; `projects/store.py:1227`). Values are `json.dumps`'d in Python and read back whole. Postgres never inspects them. **Caveat for any port:** carrying the DDL over _verbatim_ is wrong — SQLite assigns affinity by type-name matching, and a column declared `jsonb` gets **NUMERIC** affinity, so a JSON scalar document `'123'` reads back as integer `123`. These must be declared `TEXT`.

7. **pgvector / generated `tsvector` / GIN — genuinely PG-exclusive, and entirely unapplied.** All of it is confined to `library/schema.sql:242-350`, `palette/schema.sql:42-47` and `inbox/schema.sql:98-103`; none is in `MANIFEST.lock`; `pgvector` is not in `requirements.in`. The shipped desktop runs Python BM25-lite over a dict (`library/search.py:248`). Meanwhile FTS5 is compiled into the bundled interpreter's SQLite and `sqlite_vec` 0.1.9 is already staged in the packaged ai-backend site-packages. **Postgres is not buying hybrid search today; SQLite is closer to buying it than Postgres is.**

8. **The genuinely non-portable-as-written list** (short, and the honest one): `citext` (7 occurrences → `COLLATE NOCASE`, and because the cluster is `--locale=C` this is exact, not approximate); `= ANY(%s)` array binding (5 sites in backend, more in ai — `sqlite3` cannot bind a Python list at all, so these become dynamically-composed placeholder runs); `ILIKE` (2 sites → `LIKE`); `DEFAULT now()` (34 in the baseline); `CHECK (col = ANY (ARRAY[...]))` (26); `::jsonb` casts (34); 142 `timestamptz` columns; `bigserial` on a non-PK column (`0050:39,58`); bare `OFFSET` without `LIMIT` (3 sites in `mcp_revision_store.py:462,567,573`); `RETURNING tbl.*` (`runtime_api_store.py:7025`); `statement_timeout`/`lock_timeout`/`idle_in_transaction_session_timeout` (`store.py:81-95`, no SQLite equivalent beyond `busy_timeout`); RLS and `CREATE ROLE`/`GRANT`.

9. **The one argument that actually survives:** `PostgresMergeData` re-keys ~25 tables in a single transaction with a `to_regclass()` existence probe and collision-resolving deletes (`identity/account_merge.py:354-470`). That is a real multi-table ACID operation, it is reachable on desktop (linking Google to the device account, `desktop_app.py:250-252`), and it is the only place the transactional engine earns its keep. **SQLite has full ACID and would run it unchanged**; the only PG-specific dependency is the `BYPASSRLS` role note, which is moot with RLS off.

**And the counter-argument nobody in the codebase seems to have noticed:** the flagship MCP-config-save operation is _already non-atomic on Postgres today_. `write_config`'s own docstring says so: "There is no cross-row transaction available here — each registry mutation owns its own" (`service.py:624-626`), and the loop applies create/update/delete one registry call at a time (`service.py:653-671`). If the process dies mid-loop the user's config is half-applied. Whatever Postgres is buying, it is not that.

## 5. The cost of shipping it

**Disk, measured on the real staged `darwin-arm64` tree:**

- `resources/runtime/darwin-arm64/postgres` = **66 MB** — `bin` 8.6 MB, `lib` 52 MB, `share` 5.1 MB.
- Only **three** executables ship: `initdb`, `pg_ctl`, `postgres`. No `psql`, no `createdb`, no `pg_isready` — which is _why_ database creation has to shell out to a staged Python + psycopg (`postgres.ts:228-272`) and why `pg-facts.ts` does the same.
- The other 57 MB is dead weight for a single-user loopback database: 107 shared libraries (`libicudata` 27 MB, `libcrypto` 4.1 MB, `libicui18n` 2.6 MB, `libzstd`, `libxml2`, `libkrb5` — Kerberos), 88 server extension `.dylib`s (`dblink`, `postgres_fdw`, `bloom`, `pgcrypto`, plperl glue), and 5.1 MB of `share/postgresql` (2.3 MB timezone DB, 932 KB `postgres.bki`).
- Per-platform jars: darwin-arm64 30.4 MB, darwin-x64 30.4 MB, win32-x64 23.4 MB (`tools/desktop-runtime/manifest.json:40-68`).
- On macOS all 107 dylibs + 3 executables must additionally be `strip`'d and ad-hoc codesigned at stage time, in batches of 100 with per-file retry (`tools/desktop-runtime/stage.mjs:843-861`).

**Disk, measured on the live install** (`~/Library/Application Support/0xCopilot`, app not running):

| Path                                                       | Size                                                          |
| ---------------------------------------------------------- | ------------------------------------------------------------- |
| `pgdata` total                                             | **75 MB** (of which `pg_wal` is 32 MB)                        |
| `pgdata/base/16385` (`atlas_backend`)                      | 13 MB — all 79 backend tables + `_yoyo_migration`             |
| `pgdata/base/16384` (`atlas_ai`)                           | 7.4 MB — **empty shell**, 299 files, identical to `template1` |
| `pgdata/base/1`, `/4`, `/5` (template0/template1/postgres) | 7.5 + 7.3 + 7.4 MB                                            |
| `agent-data` (the file store that actually serves chat)    | **7.1 MB**                                                    |

So the app spends **75 MB of Postgres on disk to back 7.1 MB of file store plus one backend schema**, and 32 MB of that is write-ahead log.

**Boot time** (measured against the real staged binaries, into a scratch datadir):

- `initdb` = **0.55 s** — first run only, but strictly on the critical path.
- `pg_ctl -w -t 60 start` = **0.12 s** cold / 0.11 s warm on Apple Silicon (the code is written to tolerate 60 s).
- `pg_ctl -m fast stop` = 0.10 s.
- One staged-Python + psycopg spawn = **0.20 s**. A default boot pays **two** unconditionally (`ensureDatabase(atlas_backend)` + `ensureDatabase(atlas_ai)`), a **third** for the `pg-facts` probe until the file store has data, and a **fourth** for backend's `migrate.py`.
- The phases are strictly serial `await`s: `secrets → ports → postgres → migrations → services → health → ready` (`supervisor.ts:115-201`). Nothing overlaps Postgres — the three Python services are not even constructed until `pg_ctl` has returned _and_ both `CREATE DATABASE` spawns have completed _and_ yoyo has applied 13 migrations.

**Steady-state resident cost:** 6 processes — postmaster, checkpointer, background writer, walwriter, autovacuum launcher, **logical replication launcher** — ~21.7 MB RSS, for the entire life of the app.

**Failure modes the supervisor has to handle, each with code:**

1. **Stranded postmaster.** `#cleanupStalePid` reads `postmaster.pid`, `kill(pid,0)`-probes it, and if a _live_ orphan from a force-quit predecessor owns `pgdata` it issues `pg_ctl -m fast stop`, escalating to `-m immediate` (SIGQUIT, no checkpoint, crash recovery next start) if the orphan ignores SIGINT (`postgres.ts:228-272`). The comment states that without this, every subsequent launch hard-fails until the user hunts the process down.
2. **Stale PID file** from a crash — deleted before start.
3. **EPERM vs ESRCH ambiguity** — `defaultProcessAlive` treats EPERM as alive because only ESRCH proves death.
4. **Log-directory ordering** — `pg_ctl -l` opens the log file directly, so `logs/` must be `mkdir`'d before Postgres starts, ahead of the service log writers.
5. **The pwfile dance** — `initdb` refuses a non-empty `dataDir`, so the password file must live _beside_ it as `<dataDir>.pwfile`, mode 0600, deleted in a `finally` (`postgres.ts:196-226`).
6. **Unowned live postmaster** — if the owner-marker write fails (read-only userData), `start()` calls `stop()` and rethrows rather than leave a live server nobody owns.
7. **An ownership protocol** (`.0xcopilot-owner.pid`, 0600) exists solely so `copilot doctor` can distinguish this app's postmaster from a crashed host's orphan.
8. **An unrotatable password.** `BootSecretsUnreadable` (`boot-secrets.ts:7-11`) exists specifically because "a fresh `pgPassword` would lock us out of the existing database" — so an unreadable keychain becomes a fatal boot screen whose only remedy is deleting the app's data directory.
9. **Port churn.** 1 of 4 OS-allocated ports is the postmaster's; the allocator closes all listeners before returning ("a tiny window before the real service binds", `ports.ts:8-47`), and because the port is re-allocated per boot while `pgdata` is not, a reclaimed orphan cluster must be stopped before the fresh start binds a new port on the same data dir.
10. **A user-visible platform regression.** `window-all-closed` deliberately breaks the macOS keep-in-dock convention because keeping a headless supervised app alive "is what left orphaned Electron/postgres pids on CLI launches — `copilot` never returned" (`apps/desktop/main/index.ts:1081-1092`).
11. **Three CLI subcommands carry orphan logic:** `doctor` has a 4-state database classification (owned/orphaned/stale/invalid) built from `postmaster.pid` + `.0xcopilot-owner.pid` liveness probes (`tools/cli/lib/doctor.mjs:121-210`); `repair` duplicates the fast→immediate escalation and tells the user to `kill -9` by hand (`repair.mjs:33-104`); `uninstall` sweeps processes twice and retries the `rm` after 500 ms because "on macOS a just-killed postgres can hold `pgdata` for a beat" (`uninstall.mjs:186-206`).

None of 1–11 exists for an in-process store.

## 6. Options

**The constraint that governs everything: the same `services/backend` code serves self-host cloud** (`deploy/self-host/`, GHCR images, multi-tenant with real RLS and SCIM/SAML). Any port must keep both. That rules out "rewrite the queries for SQLite" as a fork; it has to be a **second adapter behind the existing seam**.

**The good news about that seam, verified:** `services/backend` has **32** `^class Postgres*` store classes, **61** `^class InMemory*` twins, and **48** store `Protocol` definitions. The desktop composition root wires **28** Postgres adapters explicitly (`desktop_app.py:193-267`) and lists 15 more stores it deliberately leaves in-memory. The port-and-adapter architecture that a SQLite backend needs **already exists and already has a second full implementation**. That is the single most important input to the effort estimates below.

**The obstacle, also verified:** the seam is bypassed in two places. `McpService._default_store` (`service.py:2429-2431`) and `SkillService._default_store` (`service.py:2828-2830`) each read `os.environ["DATABASE_URL"]` and construct `PostgresConnectionPool.shared(...)` themselves as a lazy default, so two of the hottest desktop stores can bind Postgres without going through `DesktopComposer` at all. Any port must close those first.

### (a) Keep embedded Postgres

- **What breaks:** nothing. **Effort:** 0.
- **What it buys:** one storage engine across desktop and cloud; the `PostgresMergeData` transaction stays as written; the cloud RLS story is untouched.
- **What it costs, ongoing:** everything in §5 — 66 MB, ~0.9 s of serial boot work, 6 resident processes, 75 MB of user disk, an unrotatable password, and the ~1 800 lines of supervisor + CLI code (`postgres.ts`, `pg-facts.ts`, `boot-store-backend.ts`, `migration-policy.ts`, `migration-runner.ts`, `file-store-facts.ts`, `migrations.ts`, plus `doctor`/`repair`/`uninstall` orphan handling) that exist only to babysit a separate OS process.

### (b) Port `services/backend` to SQLite (second adapter, cloud keeps Postgres)

- **What breaks:** RLS (already inert on desktop — §4.4); role GRANTs (already void on desktop — §4.5); the 4 SCIM tables and 4 SAML tables (cloud-only, need not be ported at all — the desktop can keep their in-memory twins); `= ANY(%s)` bindings; `ILIKE`; `citext`; 34 `DEFAULT now()`; 26 `CHECK (= ANY (ARRAY[…]))`; 34 `::jsonb` casts; 142 `timestamptz` columns; the `bigserial` non-PK column in `0050`; 3 bare-`OFFSET` statements. Concurrency: 15 `FOR UPDATE` sites and 5 advisory-lock sites become `BEGIN IMMEDIATE` — **and this is the one place a naive port silently corrupts data.** The desktop backend is one _process_ but not one _writer_: 50 of 51 `app.py` route handlers are sync `def` running on Starlette's threadpool against a pool of min 5 / max 50 connections (`store.py:53-58`), plus `SessionSweeper` writing from a background task. A read-modify-write like `settings/store.py:307-330` with `FOR UPDATE` merely dropped produces a **lost update**; with a deferred `BEGIN` + `busy_timeout` it produces a non-retryable `SQLITE_BUSY_SNAPSHOT`. Only `BEGIN IMMEDIATE` as the first statement is correct.
- **Effort:** **8–12 engineer-weeks.** Roughly: 2 weeks of DDL translation (a second `migrations/sqlite/` chain, ~230 column-level rewrites), 3–4 weeks writing the ~20 SQLite adapters the desktop actually needs (the other 12 stay in-memory or cloud-only), 1 week closing the two `_default_store` bypasses and the `DesktopComposer` env contract, 2 weeks on the transaction-discipline sweep (`BEGIN IMMEDIATE` + a lint gate), 1–2 weeks on the conformance suite (the pattern exists — `services/ai-backend/tests/unit/runtime_adapters/test_store_conformance.py:41-58` already parametrises `in_memory`/`file`/`postgres`).
- **What it buys:** deletes 66 MB from the installer and 75 MB from the user's disk; removes ~0.9 s and two process spawns from every boot; removes 6 resident processes; **deletes all 11 failure modes in §5**, along with `postgres.ts`, `pg-facts.ts`, the whole `boot-store-backend`/`migration-policy`/`migration-runner` carry-over subsystem, and the orphan logic in `doctor`/`repair`/`uninstall`; ends the unrotatable-password class of fatal boot screens.

### (c) Extend the file-native store to cover `backend` too

- **What breaks:** the strongest case _against_ files is here, and it comes from the file store's own docstrings. `FileRuntimeApiStore` has "**no** cross-process flock, no WAL commit-markers, no hash-chained generations, no tail-repair — those were explicitly cut" (`file/runtime_api_store.py:13-15`); every core invariant is guarded by an `asyncio.Lock`, i.e. in-process only, with no lockfile guard on `open()`. That assumption holds for ai-backend (one in-process worker) and **does not hold for `backend`** (50 threadpool handlers). Second: `open()` replays and Pydantic-validates _all_ history into RAM at every launch (`file/runtime_api_store.py:727-767`) — O(total history) time and RSS per boot. Third: the file store writes plaintext by design ("`ensure_ascii=False` so the files stay human-readable / greppable", `file/_jsonl.py:11-13`), whereas the Postgres adapter field-encrypts message and citation text; extending that design to identity tables would put session hashes and OAuth state in greppable plaintext.
- **Effort:** **12–18 engineer-weeks**, and it re-solves problems SQLite has already solved (indexed lookup, atomic multi-row transactions, crash-safe concurrent writes).
- **What it buys:** no new engine. But note the file store already concedes the point — its query engine _is_ SQLite (`file/_catalog_index.py`), and its checkpointer _is_ SQLite. Option (c) is really option (b) with a worse write path.

### (d) Hybrid — Postgres for cloud, SQLite for desktop, one adapter interface

This is what (b) actually is. Stating it separately is a category error: the cloud deployment is not going anywhere, so _every_ viable option is a hybrid. The only real question is which engine sits behind the desktop half of the seam.

### ▶ Recommendation: **(b) — a SQLite adapter for `services/backend`, Postgres retained for cloud.**

Five reasons, in order of weight:

1. **The desktop's data model is not relational, and the code says so.** 2 JOINs, 0 CTEs, 0 window functions, 0 executed `SKIP LOCKED`, 0 executed `LISTEN/NOTIFY` across 277 execute sites and 78 tables. The `connectors` table exists _specifically_ to avoid a three-way join and says so in its DDL (`connectors/schema.sql:3-8`). Cross-destination rollups are fanned out and merged in Python (`projects/rollup_sources.py:41-87`), and `home/service.py:38-42` — the module that should need cross-destination joins — deliberately has none. This is a keyed document store wearing a SQL costume, and every one of those design decisions makes a SQLite port _smaller_.
2. **The three "we need Postgres" arguments are all already switched off on desktop.** RLS: no `FORCE` in any applied migration, superuser connection, `enforce_rls=False`. `LISTEN/NOTIFY`: `RUNTIME_EVENT_BUS_BACKEND=in_memory`, one process. `SKIP LOCKED`: zero executed statements in `backend`, and the ai-backend queue the desktop actually runs is a dict under a lock.
3. **SQLite is already load-bearing on this desktop's hot path** — the file store's list/keyset/count/FTS5 read path (`file/_catalog_index.py:46-119`) and the LangGraph checkpointer (`deep_agent_builder.py:463-479`). Shipping a second engine to serve ~40 small tables while a third engine (SQLite) already serves the chat history is the actual architectural incoherence here.
4. **The seam exists.** 48 store Protocols, 32 Postgres implementations, 61 in-memory implementations, one composition root that enumerates them, and a conformance-suite pattern already proven in ai-backend. This is adapter work, not a rewrite.
5. **The failure surface deleted is disproportionate to the effort.** §5 lists 11 distinct failure modes, ~1 800 lines of supervisor/CLI code, an unrotatable secret, and a deliberate macOS convention regression — all attributable to running a second OS process. 8–12 weeks to delete that, plus 66 MB of installer and 75 MB of user disk, is a good trade.

**Sequencing, if it is taken up:** (i) close the two `_default_store` Postgres bypasses at `service.py:2431,2830` so `DesktopComposer` is genuinely the only wiring path; (ii) port the ~20 desktop-live stores only, leaving SCIM/SAML/MFA/adapter-registry/SIEM on their existing Postgres adapters for cloud and their in-memory twins on desktop — that alone cuts the schema in half; (iii) add a `BEGIN IMMEDIATE` lint gate before writing a single adapter, because the lost-update failure mode is silent; (iv) reuse the ai-backend store-conformance test shape (`test_store_conformance.py:41-58`) as the acceptance gate; (v) keep the Postgres arm as a supported rollback for one release, exactly as `boot-store-backend.ts` already does for the ai-backend store.

**One thing to fix regardless of which option is chosen:** `supervisor.ts:144-147` unconditionally `CREATE DATABASE`s `atlas_ai` on every boot, and `desktop-supervisor.ts:294-298` then skips its migrations. That is a 0.20 s process spawn and a 7.4 MB empty database directory on every install, for a database nothing connects to. Guarding it on the resolved store backend is a one-line change with zero risk.

## 7. What I could not verify

- **No live database inspection.** The bundled Postgres ships no `psql`, and the superuser password is sealed in `boot-env.bin`. Database identification in §3b is by matching printable strings extracted from each `base/<oid>` heap against the 79 `CREATE TABLE` names parsed from the migrations, corroborated by file counts (`atlas_ai` = 299 files, identical to `template1`). Strong, but not a `\dt`.
- **No packaged-app run.** I did not launch the desktop app. Boot timings were measured by invoking the real staged binaries directly into a scratch datadir; the serial-phase structure is read from `supervisor.ts`, not observed.
- **Effort estimates are judgement, not measurement.** The 8–12 / 12–18 week figures come from counting adapters, tables and rewrite sites; no spike was built. The `BEGIN IMMEDIATE` failure modes were reproduced against the shipped SQLite (3.53.1 in the staged Python), but not against a ported adapter.
- **Windows and Linux staging** were inspected only through `manifest.json` and `stage.mjs`; the 66 MB / dylib-count / codesign figures are darwin-arm64 measurements.
- **Dev/CI cost of Postgres was not audited.** The docker-compose dev stack, the live-Postgres integration suites (`services/backend/tests/integration/persistence/`), and the `postgres-restore-drill.yml` workflow all depend on a real server. That is both part of the cost of keeping Postgres _and_ part of the cost of removing it, and I did not size either.
- **`packages/audit-chain`** — the shared Python+TS hash-chain primitive under every audit table in both services — was not read. It is the one cross-cutting component that could constrain the storage engine, and the §4.3/§4.5 conclusions assume it does not.
- **I did not enumerate write-status per table for all 69 `atlas_ai` tables.** Because the Postgres arm is not taken on desktop (`factory.py:528` vs `:607`, mutually exclusive), per-table precision there does not change any conclusion. The 11 verified writer-free tables were confirmed by `INSERT INTO <table>` counts across `src/`, including f-string-constant call sites.
